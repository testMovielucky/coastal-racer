# План реализации: портретная браузерная 3D-гонка

Дата: 9 сентября 2026 года. Рабочее обозначение проекта: **Coastal Racer** — не утверждённое название.

Статус: спецификация и план, а не отчёт о реализованной или протестированной игре. Числовые параметры ниже — предлагаемые стартовые настройки и бюджеты для проверки. Производительность ещё не измерена.

## 3. Главные решения

### 3.1. Технологии

Рекомендуемый основной стек:

| Назначение | Инструмент | Причина выбора |
|---|---|---|
| Язык игры | TypeScript, строгая проверка типов | Явные контракты между системами и проверка изменений Codex |
| Сборка | Vite + npm | Статическая сборка и документированный процесс публикации на Pages [S9] |
| Движок | Обычный Babylon.js, не Babylon Lite | Набор игровых подсистем и поддержка WebGL/WebGPU [S1] |
| Базовый рендер | WebGL2 | Одна основная графическая конфигурация для первой версии |
| Физика | Babylon Physics V2 + Havok WebAssembly | Готовая интеграция столкновений и физических тел [S2] |
| Интерфейс | HTML/CSS поверх canvas | Независимая чёткость интерфейса при снижении 3D-разрешения |
| Модели | Blender → glTF/GLB | Редактируемые исходники и экспорт игровых моделей [S5, S6] |
| Оптимизация моделей | glTF Transform; выборочные операции | Проверка и обработка ассетов командной строкой [S7] |
| Сохранения | IndexedDB + idb | Транзакции для кошелька и улучшений; удобная обёртка [S13, S14] |
| Тесты | Vitest + Playwright | Логические тесты и браузерные сценарии; реальные устройства проверяются отдельно [S12] |
| Генерация маршрута | Seeded PRNG + чистый TypeScript | Воспроизводимая схема трассы без сетевых запросов |

Пакеты Babylon выбирать совместимых версий, фиксировать lockfile. Использовать только необходимые модули, не подключать отладчик движка в production. Совместимость конкретных версий Babylon и Havok проверяется первым техническим тестом.

Babylon.js выбран за интегрированные подсистемы, а не потому, что он гарантированно быстрее альтернатив. Собственная гоночная механика всё равно понадобится: готовый движок не определяет, как именно должен ощущаться этот автомобиль.

WebGPU не объявляется неподдерживаемым на iOS: в современных версиях Safari он есть [S10]. Но в MVP не нужно одновременно поддерживать два независимо настраиваемых пути рендера. Включение WebGPU возможно позднее по результатам сравнительных измерений, без обещания автоматического выигрыша.

Не нужны Python-бэкенд, Next.js, серверная база данных, мультиплеер или сторонняя аналитика. Python используется только в инструментах подготовки ассетов для Blender.

### 3.2. Бесплатная генерация ассетов: точное значение

Рекомендуемый путь: **текстовое описание/референс → Codex → Python-скрипт Blender → настоящая 3D-модель → превью → правки → GLB**.

Такой рабочий процесс с Codex, Blender Python API и запуском Blender через его executable описан OpenAI [S4]. Blender также документирует запуск Python-скриптов из командной строки [S5]. Отдельный платный генератор 3D не требуется.

Важное ограничение: это ИИ-моделирование через исполняемый код, **а не специализированная text-to-mesh модель**, напрямую выдающая полигональную сетку. Не обещать, что обычная генерация картинки создаёт GLB. Результат и в первом случае остаётся настоящей 3D-моделью, но качество сложных поверхностей спорткара нужно доказать пробным ассетом.

Это рекомендуемый способ выполнить требование «создавать по промпту через Codex/ChatGPT» в заданном бюджете. Если для заказчика принципиален именно механизм text-to-mesh, считать вопрос не закрытым, а не молча заменять его процедурными примитивами. Не добавлять сторонний сервис без отдельного решения.

Никакие API-ключи, облачная генерация и локальная нейросеть на телефоне в игру не встраиваются. Неизвестная видеокарта компьютера не используется как основание плана.

### 3.3. Карта: ИИ создаёт набор, код собирает маршрут

Ассеты и дорожные модули создаются при разработке. Перед заездом браузер собирает из этого набора новый допустимый маршрут и окружение.

Не генерировать нейросетью целый новый мир перед каждым стартом. Не объединять весь мир в один монолитный GLB. Геометрия дороги и правила прохождения должны быть контролируемыми и проверяемыми.

## 4. Управление, камера и поведение автомобиля

### 4.1. Одним пальцем

Основной игровой контакт хранится как `drivePointerId`. Начальное нажатие задаёт точку отсчёта руления. Горизонтальное смещение пальца преобразуется в сглаженную команду поворота, а не в мгновенный телепорт автомобиля поперёк дороги.

Удержание даёт газ. Отпускание задаёт нулевую целевую скорость и короткую аркадную остановку; стартовый параметр торможения — 0,2–0,4 секунды, подлежит проверке на ребёнке. После завершения торможения машина сама не едет. Ускорение не отменяет правило остановки.

Обычное отпускание пальца не ставит гонку на паузу: соперники продолжают движение. Кнопка паузы, сворачивание браузера, потеря видимости или переход в неподдерживаемую ориентацию останавливают всю локальную симуляцию. После возвращения требуется новое нажатие, старое удержание не восстанавливается.

Использовать Pointer Events, захват указателя и обработку `pointercancel`/`lostpointercapture` [S11]. Не блокировать браузерные жесты вне игрового поля. Нажатия на паузу и меню не должны давать газ.

### 4.2. Нитро без обязательного второго пальца

Нитро-кнопка — тоже допустимая точка начала основного контакта. При её нажатии тратится один заряд; при дальнейшем удержании палец продолжает давать газ и может рулить. При переходе на кнопку одним пальцем разрыв контакта вызывает обычное короткое торможение. Не сохранять скрытый газ после отпускания ради нитро.

Дополнительный второй палец может активировать нитро, пока первый рулит, но для игры это не должно быть обязательным. Второе касание не меняет `drivePointerId`, точку отсчёта и текущий угол руля. Событие активации обрабатывается один раз на нажатие; `pointerdown` и `click` не должны списывать два заряда.

Начальные предлагаемые параметры: 3 заряда на каждый заезд, 2 секунды действия, примерно +25% к максимальной скорости, без суммирования нескольких эффектов. Во время аварии, возврата, паузы, отсчёта и после финиша кнопка неактивна. Конкретные значения — баланс, не окончательная спецификация.

### 4.3. Помощь без автопилота

Машина имеет самостоятельные координаты, направление и скорость. Центральная линия дороги используется для ограниченной помощи, но не задаёт обязательную позицию.

Помощь объединяет небольшую поправку к повороту на основе ближайшего участка дороги, ограничение излишнего бокового скольжения, мягкую стабилизацию и слабое отталкивание от края. Максимальный вклад помощи ограничен и вынесен в конфигурацию.

Критическая проверка: на тестовом выраженном повороте машина при удержании газа без руления должна задеть стену или покинуть дорогу. Нельзя проходить всю трассу, просто удерживая палец неподвижно.

Одновременно небольшой промах не должен моментально выбрасывать автомобиль: проверка самостоятельной игры ребёнком проводится до настройки магазина и прогрессии.

### 4.4. Физический контроллер

На каждую машину — одно динамическое физическое тело с простым коллайдером, не коллайдер детальной модели. Двигатель и аркадное сцепление задают ограниченные силы/скорости и угловое управление. Контакт с дорогой может определяться небольшим фиксированным числом лучей. Колёса — визуальные дочерние объекты, не отдельные физические тела с подвеской.

Havok отвечает за контакт, непроникновение и импульсы. Игровой контроллер — за ограничения и ощущение управления. Не писать собственный решатель столкновений и не эмулировать взаимодействие машин только расстояниями. Не перезаписывать скорость после физического контакта так, чтобы исчезал боковой импульс.

Простые формы коллайдеров соответствуют рекомендациям по производительности Physics V2 [S3]. Высокая скорость проверяется отдельными тестами на тонких стенах и краях: при необходимости применяются доступные shape queries, подходящая толщина барьеров или подшаги. Не предполагать, что «физика подключена» автоматически исключает проскок препятствия.

### 4.5. Столкновения и восстановление

| Событие | Поведение |
|---|---|
| Контакт с другой машиной | Физический толчок, небольшой сброс скорости, короткий визуальный удар |
| Скользящий контакт со стеной | Контакт и потеря скорости, без обязательного полного переворота |
| Сильный фронтальный удар/препятствие | Короткий управляемый переворот, сброс скорости, возврат на колёса |
| Вылет с дороги | Падение, короткая задержка, возврат в безопасную точку до вылета |
| Застревание | Автоматическое восстановление после ограниченного интервала |

Управляемая анимация аварии предпочтительнее непредсказуемого длительного кувыркания. В режиме аварии явно переключаются управление, состояние физического тела и визуальная анимация; нельзя одновременно перемещать один transform анимацией и физикой.

Камера не переворачивается вместе с кузовом. После возврата возможен короткий период отключения контакта с другими машинами, чтобы не создавать бесконечную цепочку аварий. Это защита при восстановлении, а не свойство нитро.

Точка возврата выбирается из недавней истории безопасных состояний: положение на дороге, направление, участок маршрута. Проверяется отсутствие препятствия и другой машины. Возврат не переносит за непройденную контрольную точку. Монеты и заряды нитро после аварии не восстанавливаются.

### 4.6. Камера и визуальные эффекты

Камера сзади и сверху, со сглаживанием и взглядом немного вперёд по дороге. Визуальное ускорение усиливается умеренным изменением поля зрения и дистанции камеры, следом за машиной, небольшим количеством частиц и быстрым движением объектов по краям экрана.

Начать без motion blur, SSAO, экранных отражений, прозрачного объёмного стекла и тяжёлого bloom. Удар камеры короткий, небольшой и отключаемый. Настройка уменьшения тряски доступна взрослому, но не загромождает игровой экран.

## 5. Соперники и правила гонки

Пять ботов используют тот же класс автомобиля, физические тела и интерфейс команд, что игрок. Их задача — выбирать целевую скорость и направление с учётом поворота, соседей и препятствий.

Основа: следование выбранной траектории с упреждением, несколько поперечных позиций для обгона, дистанция до ближайшего автомобиля, небольшое различие параметров осторожности и скорости. Нейросеть во время заезда не нужна.

Боты не должны постоянно ездить строем, намеренно блокировать ребёнка или телепортироваться к игроку. Коррекцию сложности по отставанию не включать автоматически; сначала проверить базовый честный баланс. Возможность ограниченной настройки сложности оставить в конфигурации.

Финиш ботов не завершает заезд игрока. Финишировавшие боты перестают мешать на линии финиша. Результат игрока определяется порядком пересечения финиша после обязательных ворот. Окончательного проигрыша и лимита попыток нет.

Для ранжирования используется продвижение по маршруту, а не прямое расстояние до финиша. Для предотвращения скачков на близких участках поиск положения вдоль трассы ограничивается соседними сегментами относительно предыдущего прогресса.

## 6. Генерация новой трассы

### 6.1. Представление данных

Разделить понятия:

- `TrackTheme`: визуальная тема, набор декора, палитра и допустимые дорожные модули.
- `TrackRecipe`: версия генератора, seed, последовательность модулей и их параметры.
- `TrackRoute`: центральная линия, длина, ширина, высота, локальное направление, края, ворота.
- `TrackScene`: реальные меши, коллайдеры и декор, созданные по этим данным.
- `RaceRules`: условие финиша, число кругов и начисление наград.

Все системы читают один маршрут: боты, помощь водителю, расстановка монет, камеры, возврат, ранжирование. Не рассчитывать отдельные несовместимые кривые для каждой системы.

Seed плюс версия генератора воспроизводят **описание трассы**. Это не обещание побитово идентичной физической симуляции на разных браузерах.

### 6.2. Набор первой темы

Предлагается 8–12 семейств дорожных элементов: прямая, мягкие левые/правые повороты, S-образный участок, широкая дуга, небольшой подъём/спуск, начало, финиш и переходы. Это переиспользуемые шаблоны, не 12 отдельно огромных сцен.

Трамплины, петли, перевёрнутые участки, движущиеся барьеры и сложные развязки не считать обязательными для MVP: они не были выбраны заказчиком и увеличивают объём настройки физики.

Окружение: океан, песчаная кромка, пальмы, набережная, ограниченное число вариантов прибрежных зданий, ограждения, дорожные указатели. Это стилизованное вымышленное побережье, не точная географическая реконструкция Майами.

У модулей нужны совместимые соединения: положение, направление, ширина, высота, непрерывность касательной, единый шаг разметки. На видимых стыках не допускаются щели и ступеньки коллайдера.

### 6.3. Алгоритм

1. Выбрать новый seed и целевой диапазон длины из базового темпа машины.
2. Собрать маршрут из допустимых переходов. Использовать ограничения на кривизну, высоту и ширину; не разбрасывать случайные точки без контроля.
3. Исключить пересечения дороги, слишком близкие участки и наложение побережья на маршрут.
4. Разместить старт/финиш и ворота проверки прогресса.
5. Расставить препятствия и монеты по допустимым шаблонам, оставляя проезжаемый коридор.
6. Расставить декор на разрешённых сторонах дороги: море и берег должны оставаться согласованными с маршрутом.
7. Проверить описание; после ограниченного числа неудач использовать известную безопасную трассу.
8. Подготовить меши, физику, материалы и эффекты до отсчёта старта.

Не ставить непроходимые барьеры, препятствия в точках восстановления или предметы в слепой зоне за резким перегибом. Достижимость проверяется с учётом максимальных улучшений и нитро, а не только стандартной скорости.

### 6.4. Цена операции

Главное различие — разовая подготовка и постоянная стоимость кадра. Выбор десятков модулей и создание компактного описания не требуют генеративной модели. Количество проверок ограничивается. Загрузка файлов, декодирование текстур, создание коллайдеров и подготовка графических ресурсов измеряются отдельно.

Сначала чистая функция генерации запускается до гонки. Если проверки заметно задерживают интерфейс, она переносится в Web Worker; worker возвращает данные, а не Babylon-сцену [S15]. WebGL-объекты и сцена готовятся через основной движок на экране загрузки.

Предварительный бюджет после появления ассетов в памяти: схема маршрута — до 100 мс; подготовка играбельной сцены — порядка 1–2 секунд. Это **цели для измерения, не полученный бенчмарк**. Холодная сеть в эти значения не входит.

Во время заезда новые модели не загружаются, не компилируются материалы и не перестраивается трасса. Сборка очередной случайной карты происходит между заездами.

Разбить визуальные объекты на пространственные секции для отсечения невидимого. Thin instances подходят для повторяющегося декора [S8], но объединять всю трассу в одну группу с общими огромными границами не следует: это мешает отсекать далёкие экземпляры. В первой версии шесть машин продолжают симулироваться даже вне кадра; нельзя отключить коллайдер дороги под ботом только потому, что игрок его не видит.

## 7. Производственный процесс для ассетов

### 7.1. Первый пробный ассет

До всей игры создать один законченный спорткар и короткий художественный участок дороги. Цель — проверить форму, управляемость генерации и стоимость реального браузерного кадра.

Требования к машине: оригинальный низкий кузов современного спорткара, корректные пропорции, читаемые фары, стекло, колёса и диски, без глаз, лица и логотипов. Не копировать чужую готовую модель и не выдавать слишком грубые примитивы за финальный вид.

### 7.2. Цикл разработки

Промпт → скрипт построения → `.blend` → рендеры спереди/сзади/сбоку/под игровым углом → исправления → экспорт GLB → просмотр в Babylon с реальным освещением игры.

Картинка из ChatGPT может служить концептом, но не подменяет рендер реально созданной модели. Не принимать красивый Cycles-рендер за доказательство качества или скорости браузерной версии.

Заказчик выбирает удачные варианты и пишет художественные правки; вручную двигать вершины не требуется. Codex должен сохранять воспроизводимые скрипты, исходники и журнал важных решений.

### 7.3. Контракт автомобиля

Сохранять отдельные именованные узлы кузова и четырёх колёс. Заранее определить направление «вперёд», масштаб в метрах, центр модели и оси вращения колёс. Повторный экспорт не должен менять эти соглашения.

Предлагаемый начальный бюджет: 8–15 тысяч треугольников для ближайшей машины, упрощённый вариант для далёких ботов, 3–4 материала, преимущественно текстуры до 1024 px. Это ограничения для итерации, не гарантия FPS.

Коллайдер создаётся отдельно. Материал кузова позволяет менять цвет. Узлы и pivots будущих обвесов/дисков можно предусмотреть без реализации магазина деталей.

Оптимизация GLB должна сохранять именованные узлы и анимационные связи. Не запускать агрессивное слияние всех мешей без проверки вращения колёс. При применении Meshopt/KTX2 необходимые декодеры включаются в локальную сборку.

### 7.4. Контракт дорожного набора

Исходники модулей — редактируемые `.blend`/скрипты. Соседний JSON описывает вход/выход, границы дороги, запретные зоны декора, варианты ограждений и допустимые места предметов. Текстуры дороги бесшовные, масштаб разметки единый.

Глобальные тени одной вручную расставленной сцены нельзя запечь на весь случайный мир. Использовать локальную детализацию материалов, запечённое локальное затенение объектов и недорогой общий свет.

## 8. Производительность: обязательная часть проекта

### 8.1. Как понимать 60 FPS

Бюджет одного кадра при 60 FPS составляет примерно 16,67 мс. Проектная цель — оставлять запас, а не работать постоянно на грани этого бюджета.

Абсолютное отсутствие единственного пропущенного кадра невозможно честно гарантировать независимо от ОС, нагрева и энергосбережения. Однако устойчивые 60 FPS без регулярных провалов, создаваемых игрой, — обязательный критерий выпуска на целевых устройствах.

### 8.2. Начальные бюджеты, не результаты тестов

| Метрика | Цель для первого измеряемого билда |
|---|---|
| Частота физики | Фиксированный шаг 60 Гц |
| Активные физические машины | 6 |
| Выполнение работы кадра | Обычно с запасом до 12 мс; проверять распределение, не только среднее |
| Внутреннее 3D-разрешение | Приблизительно 0,7–1,2 мегапикселя, адаптивно |
| Вызовы отрисовки | Примерно 80–120 в типичном игровом кадре |
| Видимые треугольники | Начальная цель до 150–200 тысяч |
| Первая загрузка ресурсов | Цель до 20 МБ суммарной сетевой передачи production-сборки |
| Проверка нагрева | Непрерывная серия заездов 15–20 минут |

Числа пересматриваются по реальному профилю: небольшой полигональный бюджет сам по себе не исключает дорогих прозрачных слоёв или постобработки. Не считать их универсальными лимитами Safari.

### 8.3. Архитектурные меры

Внутреннее разрешение 3D не равно нативному DPR телефона. Интерфейс остаётся нативно чётким поверх уменьшенного canvas. Качество автоматически снижается по устойчивому замеру времени кадра, с задержкой и гистерезисом, без постоянного переключения туда-сюда.

Порядок снижения: 3D-разрешение, дорогие тени, дальний декор, плотность частиц. Не менять скорость симуляции, способности ботов или точность управления ради красивого счётчика FPS.

Начать с одного основного источника света, подготовленного окружения для отражений, простой воды и недорогих контактных теней. Реальные динамические тени добавлять только в проверенном бюджете.

Повторяющиеся объекты используют общую геометрию/материалы. Частицы, эффекты удара и монеты переиспользуются. Нет постоянных выделений массивов/объектов и DOM-обновлений всего интерфейса каждый кадр.

Физика и представление разделены. Использовать фиксированный шаг, ограниченное число догоняющих шагов и интерполяцию отрисовки. После возврата из фона не пытаться симулировать пропущенные минуты. На 120-Гц дисплее не ускорять игру в два раза.

До старта подготовить все используемые в заезде материалы и первый показ эффектов. После повторного запуска освобождать сущности прошлого заезда, но сохранять общие ассеты. Считать количество мешей, тел, материалов и обработчиков между рестартами.

### 8.4. Как проверять

Нужен встроенный диагностический экран: версия сборки, браузер, рендерер, seed, число объектов/тел, draw calls, разрешение canvas, длительность генерации, статистика кадров, текущий пресет качества. Выгрузка результата — JSON.

Браузерные автотесты на Windows проверяют сценарии и UI. Playwright эмулирует параметры устройства, но это не измерение GPU, нагрева и Safari на физическом iPhone/iPad [S12]. Финальный перформанс-тест обязателен на всех трёх устройствах заказчика.

Условия протокола: точная версия iOS/iPadOS, браузера и билда; энергосбережение выключено; зарядка и температура отмечены; тесты холодного старта, прогретого заезда и серии гонок. Записывать среднюю частоту, p95/p99 времени работы кадра и число длинных кадров. Контролировать, что максимальное нитро и кучное столкновение шести машин не создают повторяемых провалов.

## 9. Экономика и сохранение

### 9.1. Улучшения

Предлагаемый MVP-магазин: максимальная скорость, разгон, длительность нитро; до 5 уровней каждого параметра. Количество зарядов остаётся равным трём. Конкретные проценты, цены и пределы хранятся в конфигурации.

Первая покупка должна быть достижима приблизительно за 2–3 завершённых обычных заезда. Даже последнее место приносит фиксированную награду. На первых трёх местах добавляется бонус, не заменяющий базовую награду.

Стартовая схема для балансировки: 100 монет за финиш, подобранные монеты дополнительно, бонусы 100/60/30 за первое/второе/третье места. Это не подтверждённый игровой баланс. Проверять, чтобы выбор улучшений был понятен без сложного текста и чтобы скорость не разрушала управляемость для четырёхлетнего ребёнка.

Нет ежедневных серий, платных пополнений, рекламы за награду или случайных платных ящиков. Нитро пополняется бесплатно в начале каждого нового заезда.

### 9.2. Сохранение

Кошелёк, уровни улучшений, настройки, версия схемы и идентификаторы уже выплаченных наград сохраняются в IndexedDB. Для нового проекта использовать отдельное имя БД, не пересекающееся с KidsPuzzles на том же GitHub Pages origin.

Заезд имеет `raceId`; монеты имеют уникальные `pickupId` внутри заезда. При аварии собранная монета не возникает снова. После финиша награда и отметка о выплате записываются одной транзакцией. Повторное открытие результата или двойной клик не начисляют награду повторно. Покупка улучшения и списание денег тоже атомарны. Завершать показ «сохранено» только после успешной транзакции.

Предлагается начислять подобранные монеты в кошелёк при завершении гонки. Авария их не отнимает. Полное возобновление незавершённого заезда после закрытия вкладки не входит в MVP; выход из гонки требует понятного предупреждения о потере незавершённого результата.

Добавить экспорт/импорт прогресса в JSON с валидацией. Данные браузера не гарантированы навсегда: возможны очистка пользователем и вытеснение хранилища [S14]. Запрос persistent storage допустим, но не заменяет резервную копию и не является гарантией.

Прогресс не синхронизируется между устройствами. Не обещать автоматическое совпадение хранилищ вкладки Safari и установленной веб-версии без проверки этого сценария.

## 10. Интерфейс, PWA и публикация

Основные экраны: старт/гараж → подготовка трассы → гонка → результат → улучшения. Пауза и настройки открываются поверх игры. Смена темы трассы представлена данными, хотя доступна только одна тема.

Обучение — короткая анимация жеста и последовательное объяснение «держи — едешь», «двигай — поворачиваешь», «молния — ускорение». Не требовать чтения длинных инструкций. HUD: место, прогресс маршрута, монеты текущего заезда, три заряда и пауза.

На телефоне учитывать safe area сверху/снизу. На iPad не растягивать картинку: сохранять корректную перспективу и игровую композицию, допуская больше бокового обзора. В альбомной ориентации ставить гонку на паузу и показывать просьбу повернуть устройство. Manifest `orientation` и доступный Orientation API использовать как дополнение, не как единственную защиту [S16].

На ПК — клавиатура: удержание W/стрелки вверх для газа, A/D или стрелки для поворота, Space для нитро, Esc для паузы. Мышь может использовать тот же механизм удержания, что телефон.

Для Pages использовать корректный `base`, пути GLB/текстур/WASM относительно приложения, автоматическую сборку GitHub Actions [S9]. Во время игры не тянуть движок, шрифты, физику и декодеры с чужих CDN. В deployment попадают только runtime-ассеты, не тяжёлые исходники Blender.

GitHub Pages поддерживает статический вариант проекта; опубликованный сайт ограничен 1 ГБ, мягкий лимит трафика — 100 ГБ/месяц [S17]. Это не безлимитный хостинг для большой аудитории. Доступность из РФ здесь опирается на опыт заказчика с KidsPuzzles; отдельно проверяются именно домен и все ресурсы новой игры.

Для добавления на главный экран: manifest, иконки, корректные `start_url` и `scope` внутри каталога проекта, standalone-представление. В MVP не реализовывать service worker с обещанием офлайн-работы; обычный HTTP-кеш допустим. Установка с главного экрана и гарантированная офлайн-игра — разные требования. Актуальный WebKit описывает запуск сайтов с главного экрана как веб-приложений [S10].

## 12. Поэтапный план и критерии перехода

### Этап 0. Репозиторий и диагностический стенд

Настроить TypeScript/Vite, Babylon/Havok, проверки типов, тесты, корректную публикацию и диагностическую панель. Проверить версии Node/Blender и воспроизводимость команд на Windows. Получить запуск production-сборки на всех целевых устройствах.

**Готово:** сцена с шестью простыми физическими кузовами запускается с Pages, версия сборки видна, доступны отчёты, нет зависимости от CDN. Это технический стенд, не визуальный MVP.

### Этап 1. Доказательство качества ассетов

Создать спорткар и короткий прибрежный участок через Codex/Blender. Настроить игровое освещение, экспорт, именованные колёса и смену цвета. Сохранить рендеры и браузерные снимки под игровым углом.

**Готово:** заказчик принимает автомобиль и направление визуала как достаточно близкие к референсу; есть настоящий оптимизированный GLB и воспроизводимый исходник. Если качество не принято, не выдавать primitives за финальную игру и не уходить в магазин.

### Этап 2. Управление и аварии на фиксированной трассе

Сделать удержание/остановку, руление, ограниченную помощь, камеру, нитро, контакт со стеной и другой машиной, переворот и возврат. Добавить автоматические проверки состояний ввода.

**Готово:** одним пальцем удобно пройти тестовый маршрут; без руления выраженный поворот не проходится; нитро работает без обязательного второго пальца; не остаётся зажатого газа; после аварии можно продолжить. Заказчик проверяет самостоятельную игру ребёнком.

### Этап 3. Полный вертикальный срез

Добавить 5 ботов, монеты, старт, финиш и результат на одной пока фиксированной трассе. Все шесть машин используют общую физическую модель. Выполнить первый стресс-тест с одновременным контактом машин и нитро.

**Готово:** от запуска до результата можно пройти законченный заезд, финиш последним допустим; шесть машин не создают неустранимых заторов; базовый графический пресет держит целевые 60 FPS на устройствах.

### Этап 4. Пересборка побережья

Подготовить совместимые модули, генератор с seed, валидатор, расстановку предметов и декора. Включить новый маршрут перед каждым стартом и диагностическое воспроизведение по seed.

**Готово:** разные заезды действительно имеют разную геометрию; нет щелей, пересечений, неверных контрольных точек или тупиков; аварии воспроизводимы по seed. Выполнить 10 000 проверок описаний трасс и отдельный набор автоматических физических прохождений на представительных seed; это разные типы проверки.

### Этап 5. Экономика и сохранение

Гараж, три вида улучшений, награды, транзакции, импорт/экспорт. Проверить покупку последнего уровня, нехватку денег, двойной клик, повторный показ результата, миграцию и ошибку записи.

**Готово:** деньги и улучшения не теряются при обычном перезапуске и не дублируются; первая покупка достижима за несколько финишей; трассы проверены с максимальной машиной и нитро.

### Этап 6. Финальный визуал и интерфейс

Привести все модули к принятому качеству, доделать анимации, частицы, HUD, onboarding, паузу, safe areas, планшетную композицию и портретное ограничение. Подключить только отключённый звуковой интерфейс, без фиктивной готовой озвучки.

**Готово:** нет временных моделей, отладочных надписей и необработанных состояний загрузки; эффекты не скрывают дорогу; взрослый и ребёнок могут понять состояние игры без инструкции разработчика.

### Этап 7. Производительность и устойчивость выпуска

Это итоговая проверка, а не первая оптимизация. Сравнить целевые устройства, версию из браузера и с главного экрана, серию рестартов, нагрев, сворачивание, смену ориентации, медленную загрузку и ошибки ресурсов. При проблемах снижать графическую нагрузку, не требования к управлению.

**Готово:** сохранены реальные протоколы замеров; устойчивые 60 FPS в рабочем пресете; нет роста количества ресурсов после рестартов; нет блокирующих ошибок; работа с Pages проверена.

### Этап 8. Финальная приёмка самостоятельной игры

Проверить первый запуск без чтения, первый поворот, контакт с ботом, использование нитро, финиш последним и покупку улучшения. Отдельно проверить несколько последовательных заездов взрослым.

**Готово:** маленькая законченная игра соответствует принятому визуалу, объясняет себя, допускает ошибки и имеет небольшой вызов. Внешняя привлекательность без приятного управления не считается завершённым MVP.

## 14. Правила работы с Codex

Хранить короткие обязательные ограничения и рабочие команды в `AGENTS.md`; подробности — в этом плане. Codex поддерживает инструкции проекта через `AGENTS.md` [S18]. Для каждого этапа ставится отдельная задача с конкретным результатом и проверкой. Не просить «сделай всё приложение за один проход».

После задачи Codex должен сообщить: что изменено; какие команды реально запущены; что подтвердили автоматические тесты; что ещё требует устройства/визуальной приёмки; изменился ли бюджет производительности. Не выдавать успешный build за доказательство 60 FPS на iPad.

Правила для AGENTS.md:

- Не менять стек, механику управления и границы MVP без записи решения.
- Не добавлять рекламу, платежи, платные API, аккаунты и сервер.
- Не скачивать чужие игровые модели вместо требуемых сгенерированных ассетов.
- Не называть 2D-картинку 3D-моделью.
- Пользоваться Babylon/Havok для подсистем движка; писать свою игровую логику, не собственный решатель физики.
- Не выполнять генерацию ассетов и загрузку новых файлов в активном заезде.
- Сохранять seed/version и диагностические отчёты; не заявлять физическую детерминированность без проверки.
- Проверять ввод, ресайз, pause/resume и dispose при изменении жизненного цикла.
- Не отключать тесты ради зелёного статуса и не фабриковать аппаратные результаты.
- Не править одновременно несвязанные подсистемы без необходимости.
- Не перезаписывать принятые ассеты без сохранения исходника/версии.
- Работа через локальные скрипты Blender; дополнительный MCP не обязателен и не должен становиться блокирующей зависимостью.

## 15. Главные риски и меры

| Риск | Мера |
|---|---|
| Спорткар не получается близким к референсу | Ранний пробный ассет, несколько ракурсов, приёмка в браузере |
| ИИ создаёт красивую, но тяжёлую модель | Бюджет ассета, простые материалы, LOD, проверка экспортированного GLB |
| Помощь превращает игру в автопилот | Тест поворота без руления, ограниченные параметры помощи |
| Управление слишком трудно ребёнку | Практическая проверка до экономики и декоративного наполнения |
| Случайная трасса непроходима | Ограниченная грамматика, валидатор, пробные заезды, fallback |
| Просадки в столкновениях и нитро | Физический стресс-тест шести машин на раннем этапе |
| Потеря прогресса | Транзакции, версии схемы, экспорт, честное предупреждение о локальности |
| Разрастание MVP | Не включать круги, новый автопарк, музыку и динамические препятствия до выпуска |
| Эмуляция принята за аппаратный тест | Отдельные реальные протоколы трёх устройств |
| Слишком большой объём загрузки | Runtime-only assets, компрессия, отсутствие исходников Blender в dist |
